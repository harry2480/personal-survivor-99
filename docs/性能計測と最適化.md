# 性能計測と最適化

要件定義 §85 CPU最適化候補 / §102 Frame Rate / §105 Performance Requirements に対する計測と判断の記録（Issue #55）。

**当て推量で最適化しない。**計測 → 手を入れる → 計測し直す、の順で進める。

---

## 1. 計測のしかた

| 道具 | 測るもの | 実行 |
|---|---|---|
| `tools/profile_battle.gd` | 99 人戦の 1 フレームの内訳（部位ごと） | `scripts/profile-battle.sh` |
| `tools/benchmark_battle_scaling.gd` | Player 数ごとの負荷 | `scripts/benchmark-battle-scaling.sh` |
| `tools/benchmark_cpu_scheduling.gd` | CPU 更新の分散の効き方 | `scripts/benchmark-cpu-scheduling.sh` |
| `tools/benchmark_cpu_search.gd` | 配置探索 1 手の時間 | `scripts/benchmark-cpu.sh` |
| `tools/verify_determinism.gd` | 同じ Seed から同じ決着になるか | `scripts/verify-determinism.sh` |

いずれも **Simulation だけ**を測る（描画は含まない）。描画込みの FPS は実機で測る（#57）。

Godot 標準の Profiler（エディタ）は対話操作が要るため、同じ内訳を headless で取れるようにしたのが
`profile_battle.gd`。`CpuBattleRunner.step()` と同じ順に同じ処理を実行し、部位ごとに分けて測る
（Human の操作 / Battle Layer / CPU / 状態の写し / Target / Attack の配送と脱落 / 指標の読み出し）。

最適化前は main（#110 まで）、最適化後は本 Issue の変更後。同じ `profile_battle.gd` で測った。

### 最適化前

### 以前の計測（2026-09-22）について

以前の `profile_battle.gd` は Attack の配送・状態の写し・脱落の判定を実行しておらず、
Garbage も KO も起きない Battle を測っていた（その計測では合計 6.62 ms → 0.52 ms、12.7 倍速）。
実際の `step()` と同じ処理を測るように直し、前後とも測り直したのが上の表。

## 3. 実施した最適化（計測に基づく）

### 3.1 Target 選択の候補配列をやめた（37% の項目）

99 人ぶん、毎フレーム「自分以外の生存者」の配列を作り直していた（99 × 98 要素の確保）。

- 候補の一覧は **1 巡につき 1 回**だけ作り、全員で使い回す
- 「自分を飛ばして n 番目」を O(1) で引けるよう、位置の対応表を持つ
- 乱数の引き方・同点の崩し方は変えていない

### 3.2 使わない盤面を進めるのをやめた（57% → 最大の項目）

Lightweight Simulation の CPU（要件定義 §82）は盤面を使わないのに、
`BattleManager` が 98 人ぶんの `PuzzleSession` を毎フレーム進め、危険度の再計算まで行っていた。

- `BattlePlayerState.simulates_board` を足し、Lightweight の CPU では `false`
- 切り替えは `CpuManager`（Promotion / Demotion）が行う
- Detailed へ昇格したら `true` に戻る

### 3.3 結果が変わっていないことの確認

`scripts/verify-determinism.sh` を最適化の前後で実行し、3 つの Seed で**上位 10 位と終わり方（時間切れ / 決着）が完全に一致**することを確認した。
実際の Battle と同じ上限（`CpuBattleRunner.DEFAULT_TIME_LIMIT_SEC` = 300 秒）まで進めて比べている。

```text
seed=20260922  1:P97 2:P84 3:P67 4:P23 5:P5 6:P2 7:P68 8:P85 9:P9 10:P83（時間切れ）
seed=1         1:P89 2:P59 3:P39 4:P5 5:P35 6:P78 7:P3 8:P70 9:P93 10:P34（時間切れ）
seed=999       1:P23 2:P95 3:P62 4:P51 5:P10 6:P50 7:P82 8:P37 9:P92 10:P56（時間切れ）
```

## 4. 最適化候補の採否（要件定義 §85）

| 候補 | 採否 | 理由 |
|---|---|---|
| Update 分散 | **採用**（#47） | CPU 更新の p99 が 0.084 ms → 0.015 ms（8 分割）。重いフレームが減る |
| Search 回数制限 | **採用**（#39 / #47） | `MAX_SEARCH_DEPTH = 2`。深さ 3 は 1 手 3.2 秒で実用外。負荷時は Lookahead → Beam Width の順に削る |
| Cache（候補の使い回し） | **採用**（本 Issue 3.1） | Target 選択が 4.0 倍速。結果は変わらない |
| Memoization（評価値の記憶） | **不採用** | 盤面はほぼ毎回違うため当たらない。Lightweight が主体の現構成では CPU の更新自体が全体の 1.8% |
| Multithreading / WorkerThreadPool | **不採用** | Simulation が予算の 5%。並列化の複雑さ（決定論の維持・Seed 再現性）に見合わない |
| GDExtension（C++ 化） | **不採用** | 下記 5. |

## 5. GDExtension の導入判断

**導入しない。**

| 判断材料 | 数字 |
|---|---|
| 99 人戦の Simulation | 1 フレーム 0.83 ms（予算 16.67 ms の 5.0%） |
| いちばん重い部位 | Target 選択 0.49 ms |
| GDScript のままでの余裕 | 予算の 95% が残っている |

導入すると、ビルド環境（各アーキテクチャ向けのコンパイル）・配布（`.dylib` の同梱と署名）・
デバッグのしやすさが一段複雑になる。**得られるのは既に余っている時間**なので、いまは見合わない。

### 見直す条件

次のどれかに当てはまったら測り直して再判断する。

- Detailed CPU の数を増やし、探索が 1 フレームの予算の 30% を超えたとき
- 描画込みの実測（#57）で 60 FPS に届かず、原因が Simulation 側だったとき
- Lightweight の近似をやめて 99 体すべてを Detailed にする方針へ変えたとき

---

## 6. 残っている確認

- **描画込みの平均 FPS**（MVP 受入条件 28）は実機でしか測れない。#57 の実機検証で確認する
- Simulation 側は `tests/integration/test_battle_scaling.gd` が 99 人戦の 1 フレーム平均を見張っており、
  予算を超えると失敗する

## 7. メモリの検証（Issue #56）

### 計測のしかた

| 道具 | 測るもの | 実行 |
|---|---|---|
| `tools/stress_battles.gd` | 連続試合（50 回）でのメモリと Object 数の推移。増分で合否を判定する | `scripts/stress-battles.sh`（CI 外。Release 前に実行） |
| `tests/integration/test_long_session.gd` | 試合・画面の出し入れで Object が増えないこと（メモリ量は見ない） | `scripts/run-tests.sh`（CI） |

`scripts/run-tests.sh` は Godot の終了時に `resources still in use at exit` が出ると失敗する。
これが最初の網になっていて、テストのたびに解放漏れを検出している。

### 合否の決め方

`stress_battles.gd` は 10 試合目を起点に、50 試合目までの増分で判定する（最初の試合で確保される
キャッシュなどを外すため）。許容は**試合数に比例させない**固定値。比例させると、1 試合ごとに
少しずつ残るリークを見逃す。

| 項目 | 許容（10 → 50 試合） |
|---|---|
| 静的メモリ | +0.5 MB |
| Object 数 | +2 |

超えたら終了コード 1 で終わり、`scripts/stress-battles.sh` が失敗する。

`test_long_session.gd` も同じ考え方で、繰り返した回数によらない固定の許容にしている。
Scene の出し入れ（Battle 開始 → Pause → Main Menu）は 1 回ごとに Scene の切り替えを待ってから数える。
Scene の切り替えでは Object 数が ±8 程度揺れる（実測）ため、30 回繰り返して +12 までを許す。
1 回に 1 個でも残れば 30 以上増えるので見逃さない（わざとリークを入れて失敗することを確認した）。

### 計測結果（2026-09-28 / Apple Silicon / Godot 4.7.2 / 30 人戦 × 50 試合）

| 試合 | 静的メモリ (MB) | Object 数 | 孤立 Node 数 |
|---|---|---|---|
| 0 | 26.94 | 1573 | 1 |
| 10 | 26.97 | 1573 | 1 |
| 20 | 26.97 | 1573 | 1 |
| 30 | 26.98 | 1573 | 1 |
| 40 | 26.98 | 1573 | 1 |
| 50 | 26.98 | 1573 | 1 |

判定: 合格（10 → 50 試合で メモリ +0.00 MB / Object +0）。**50 試合を通してメモリも Object 数も横ばい。**

1 フレームの時間の推移は `test_long_session_keeps_the_pace` で見ているが、測っているのは
**20 人戦の Simulation 20 秒ぶん**（前半 600 フレーム / 後半 600 フレーム）だけ。数分以上続けたときの
悪化はこのテストでは分からない。長時間の挙動は下の「残っている確認」の実機検証で見る。

### 参照の持ち方について分かったこと

Runner は method の `Callable` で購読している。これは相手を**強参照しない**（Object ID を持つだけ）ため、
`dispose()` を忘れても循環にならず解放される。**lambda で `self` を捕まえた購読だけが循環する**ので、
`GarbageRouter` / `KoSystem` にある `dispose()` はその形のために残してある。

テスト（`test_battle_without_dispose_also_releases`）でこの前提を固定した。
購読の書き方を lambda へ変えるとこのテストが落ちるので、そのとき気づける。

### 残っている確認

**長時間の実機プレイ**（何十分も続けたときの挙動）は headless では測れない。#57 の実機検証で確認する。
