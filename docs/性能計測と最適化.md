# 性能計測と最適化

要件定義 §85 CPU最適化候補 / §102 Frame Rate / §105 Performance Requirements に対する計測と判断の記録（Issue #55）。

**当て推量で最適化しない。**計測 → 手を入れる → 計測し直す、の順で進める。

---

## 1. 計測のしかた

| 道具 | 測るもの | 実行 |
|---|---|---|
| `tools/profile_battle.gd` | 99 人戦の 1 フレームの内訳（部位ごと） | `scripts/profile-battle.sh` |
| `tools/benchmark_battle_scaling.gd` | Player 数ごとの負荷 | `scripts/benchmark-battle-scaling.sh` |
| `tools/benchmark_cpu_scheduling.gd` | CPU 更新の分散の効き方 | `scripts/benchmark-cpu-scheduling.sh` |
| `tools/benchmark_cpu_search.gd` | 配置探索 1 手の時間 | `scripts/benchmark-cpu.sh` |
| `tools/verify_determinism.gd` | 同じ Seed から同じ決着になるか | `scripts/verify-determinism.sh` |

いずれも **Simulation だけ**を測る（描画は含まない）。描画込みの FPS は実機で測る（#57）。

Godot 標準の Profiler（エディタ）は対話操作が要るため、同じ内訳を headless で取れるようにしたのが
`profile_battle.gd`。`CpuBattleRunner.step()` と同じ順に同じ処理を実行し、部位ごとに分けて測る
（Battle Layer / CPU / 状態の写し / Target / Attack の配送と脱落 / 指標の読み出し）。

## 2. 計測結果（2026-09-27 / Apple Silicon / Godot 4.7.2 / Seed 20260922 / 1800 フレーム）

最適化前は main（#110 まで）、最適化後は本 Issue の変更後。同じ `profile_battle.gd` で測った。

### 最適化前

| 部位 | 1 フレーム平均 (ms) | 割合 |
|---|---|---|
| `battle_update` | 3.0552 | 56.4% |
| `target_update` | 2.0304 | 37.5% |
| `battle_sync` | 0.1401 | 2.6% |
| `attack_dispatch` | 0.1202 | 2.2% |
| `cpu_indicators` | 0.0514 | 0.9% |
| `cpu_update` | 0.0184 | 0.3% |
| **合計** | **5.4156** | 100% |

1 フレームの予算（16.67 ms）の 32% を Simulation が使っていた。

### 最適化後

| 部位 | 1 フレーム平均 (ms) | 割合 | 変化 |
|---|---|---|---|
| `target_update` | 0.4785 | 59.9% | **4.2 倍速** |
| `battle_sync` | 0.1289 | 16.1% | 手を入れていない |
| `attack_dispatch` | 0.1155 | 14.5% | 手を入れていない |
| `cpu_indicators` | 0.0500 | 6.3% | 手を入れていない |
| `cpu_update` | 0.0140 | 1.8% | 手を入れていない |
| `battle_update` | 0.0116 | 1.4% | **263 倍速** |
| **合計** | **0.7985** | 100% | **6.8 倍速** |

予算の 5% まで下がった。

### 以前の計測（2026-09-22）について

以前の `profile_battle.gd` は Attack の配送・状態の写し・脱落の判定を実行しておらず、
Garbage も KO も起きない Battle を測っていた（その計測では合計 6.62 ms → 0.52 ms、12.7 倍速）。
実際の `step()` と同じ処理を測るように直し、前後とも測り直したのが上の表。

## 3. 実施した最適化（計測に基づく）

### 3.1 Target 選択の候補配列をやめた（37% の項目）

99 人ぶん、毎フレーム「自分以外の生存者」の配列を作り直していた（99 × 98 要素の確保）。

- 候補の一覧は **1 巡につき 1 回**だけ作り、全員で使い回す
- 「自分を飛ばして n 番目」を O(1) で引けるよう、位置の対応表を持つ
- 乱数の引き方・同点の崩し方は変えていない

### 3.2 使わない盤面を進めるのをやめた（56% → 最大の項目）

Lightweight Simulation の CPU（要件定義 §82）は盤面を使わないのに、
`BattleManager` が 98 人ぶんの `PuzzleSession` を毎フレーム進め、危険度の再計算まで行っていた。

- `BattlePlayerState.simulates_board` を足し、Lightweight の CPU では `false`
- 切り替えは `CpuManager`（Promotion / Demotion）が行う
- Detailed へ昇格したら `true` に戻る

### 3.3 結果が変わっていないことの確認

`scripts/verify-determinism.sh` を最適化の前後で実行し、3 つの Seed で**上位 10 位が完全に一致**することを確認した。

```text
seed=20260922  1:P97 2:P71 3:P67 4:P66 5:P45 6:P32 7:P25 8:P5 9:P2 10:P86
seed=1         1:P93 2:P92 3:P89 4:P78 5:P59 6:P55 7:P39 8:P35 9:P5 10:P3
seed=999       1:P95 2:P62 3:P56 4:P51 5:P50 6:P37 7:P23 8:P10 9:P82 10:P21
```

## 4. 最適化候補の採否（要件定義 §85）

| 候補 | 採否 | 理由 |
|---|---|---|
| Update 分散 | **採用**（#47） | CPU 更新の p99 が 0.084 ms → 0.015 ms（8 分割）。重いフレームが減る |
| Search 回数制限 | **採用**（#39 / #47） | `MAX_SEARCH_DEPTH = 2`。深さ 3 は 1 手 3.2 秒で実用外。負荷時は Lookahead → Beam Width の順に削る |
| Cache（候補の使い回し） | **採用**（本 Issue 3.1） | Target 選択が 4.2 倍速。結果は変わらない |
| Memoization（評価値の記憶） | **不採用** | 盤面はほぼ毎回違うため当たらない。Lightweight が主体の現構成では CPU の更新自体が全体の 1.8% |
| Multithreading / WorkerThreadPool | **不採用** | Simulation が予算の 5%。並列化の複雑さ（決定論の維持・Seed 再現性）に見合わない |
| GDExtension（C++ 化） | **不採用** | 下記 5. |

## 5. GDExtension の導入判断

**導入しない。**

| 判断材料 | 数字 |
|---|---|
| 99 人戦の Simulation | 1 フレーム 0.80 ms（予算 16.67 ms の 4.8%） |
| いちばん重い部位 | Target 選択 0.48 ms |
| GDScript のままでの余裕 | 予算の 95% が残っている |

導入すると、ビルド環境（各アーキテクチャ向けのコンパイル）・配布（`.dylib` の同梱と署名）・
デバッグのしやすさが一段複雑になる。**得られるのは既に余っている時間**なので、いまは見合わない。

### 見直す条件

次のどれかに当てはまったら測り直して再判断する。

- Detailed CPU の数を増やし、探索が 1 フレームの予算の 30% を超えたとき
- 描画込みの実測（#57）で 60 FPS に届かず、原因が Simulation 側だったとき
- Lightweight の近似をやめて 99 体すべてを Detailed にする方針へ変えたとき

---

## 6. 残っている確認

- **描画込みの平均 FPS**（MVP 受入条件 28）は実機でしか測れない。#57 の実機検証で確認する
- Simulation 側は `tests/integration/test_battle_scaling.gd` が 99 人戦の 1 フレーム平均を見張っており、
  予算を超えると失敗する
