# Project 99 アーキテクチャ設計規約

Godot Engine 4.x Stable + Typed GDScript による macOS 向け 99 人対戦型落ちものパズルの設計規約。
プロジェクト全体に適用する。仕様の一次情報は [要件定義.md](要件定義.md) とし、本書はその実装規約を定める。

---

## レイヤー構造

```text
Presentation Layer
        ↓
Battle Layer
        ↓
Game Core Layer
```

**依存方向を逆転させない。** 下位層は上位層の存在を知らない。

| 層 | ディレクトリ | 責務 |
|---|---|---|
| Presentation | `scenes/` `ui/` `audio/` | 盤面描画、Opponent Grid、HUD、メニュー、エフェクト、Audio |
| Battle | `battle/` `cpu/` | 99 人の Battle 進行、Targeting、Garbage Routing、KO、Ranking、Multiplier、CPU AI |
| Game Core | `core/` | Board、Piece、Rotation、Lock、Line Clear、Attack 計算、Garbage |
| 横断 | `input/` `config/` | Input Action → Game Command 変換、Rule / Balance データ |

## Game Core Layer

担当する責務:

Board / Piece / Piece Queue / Rotation / Collision / Gravity / Lock / Hold /
Line Clear / Combo / Back-to-Back / T-Spin / Perfect Clear / Attack Calculation / Garbage

**Game Core は以下を知らない（参照・import 禁止）。**

- UI
- Audio
- Controller（物理デバイス、ボタン番号）
- Scene / Scene Tree
- Animation
- File System
- Opponent Grid

原則:

- 可能な限り**決定論的な状態遷移**として実装する。同じ Seed と同じ入力列からは同じ結果が出ること
- 時間は実時間ではなく、外部から与えられる delta / tick として受け取る
- 乱数は共有の `RandomNumberGenerator` を Seed 付きで注入する。`randi()` 等のグローバル乱数を直接使わない
- Render FPS によってシミュレーション結果を変えない（[要件定義.md §102](要件定義.md)）

---

## Battle Layer

担当する責務:

Battle Player / Human Player / CPU Player / Targeting / Garbage Routing /
KO / Ranking / Attack Multiplier / Remaining Players / Battle Phase / Win-Lose 判定

原則:

- Game Core を**利用する側**であり、Game Core から参照されない
- Player の種別は `LOCAL_HUMAN` / `CPU` / `REMOTE_HUMAN` を型として定義し、MVP では前 2 種のみ使用する。
  将来の Online 対応で分岐を増やさずに済む形にする（[要件定義.md §46, §133](要件定義.md)）
- CPU は Battle Layer の内部実装。Game Core に CPU 固有の分岐を持ち込まない
- CPU は Game Core と同じ Game Command 列を生成して盤面を操作する。CPU 専用の盤面書き換え経路を作らない

---

## Presentation Layer

担当する責務:

Player Board / Opponent Boards / HUD / Main Menu / Settings / Result / Effects / Animation / Audio / BGM

原則:

- **UI から Game Core / Battle の内部状態を直接変更しない。** 変更は Command または Signal 経由で行う
- UI は Signal を購読して描画を更新する。毎フレーム全状態をポーリングしない
- Danger 判定などの**ゲーム的判定を UI 側で独自に行わない**。判定結果を下位層から受け取る（[要件定義.md §92](要件定義.md)）

---

## Input アーキテクチャ

```text
Physical Device
↓
Godot Input
↓
Input Action
↓
Game Command
↓
Game Core
```

- ゲームロジックでは**物理ボタン番号を扱わない**
- Game Command は `move_left` / `move_right` / `soft_drop` / `hard_drop` /
  `rotate_left` / `rotate_right` / `hold` / `pause` 等の抽象名で定義する
- Keyboard / Gamepad の差は `input/` 層で吸収する。Remapping も同層で完結させる
- Human Input の処理は常に最優先。CPU の思考負荷で入力が遅延する実装にしない（[要件定義.md §84, §103](要件定義.md)）

## 状態・型の設計（Typed GDScript）

- 型注釈を必ず使用する。関数は戻り値型を明示する
- `Dictionary` を状態の器として乱用しない。状態は専用 Class / Resource として定義する
- Magic Number を書かない。定数化するか `config/` のバランスデータへ出す
- Global State（Autoload Singleton）は最小限にする
- 盤面の内部行数（Spawn Buffer を含む `10 × 40` 等）は定数として定義し、表示領域 `10 × 20` と区別する

```gdscript
var score: int = 0
var player_id: int
var active_piece: PieceState
var opponents: Array[BattlePlayerState] = []
```

## Event / Signal 設計

層をまたぐ通知は Signal で行い、直接参照を増やさない。代表的な Event:

```text
piece_spawned
piece_locked
line_cleared
attack_generated
garbage_received
target_changed
player_ko
rank_changed
multiplier_changed
battle_phase_changed
battle_finished
controller_connected
controller_disconnected
```

- Signal は「起きた事実」を渡す。受け手に処理を指示しない
- 下位層は上位層の Signal を購読しない

## 決定論と Seed

- Seed を指定可能にする。用途は Bug Reproduction / Automated Test / CPU Comparison / Replay / Benchmark
- MVP で Replay 機能は必須ではないが、`Seed + Input Sequence` で再現できる構造を保つ

---

## Coding Rules

原則は以下のとおり。命名・型・Signal・ファイル分割の具体的な書き方は
[コーディング規約.md](コーディング規約.md) を参照。

- Typed GDScript
- Single Responsibility。巨大 Manager を作らない
- Game Logic と UI を分離する
- Magic Number 禁止
- Balance Parameter を外部化する
- Signal / Event で疎結合化する
- Singleton 乱用禁止
- Scene Tree への過度な依存禁止（ロジックが `get_node()` のパスに依存しない）
- Public API を明示する。内部専用のメンバーは `_` 始まりにする
- Performance Optimization は計測後に行う

## 設計優先順位

```text
Input Responsiveness
>
Correct Game Logic
>
Playability
>
Stable Performance
>
CPU Strength Scalability
>
Visual Fidelity
```

CPU を強くするために Human Player の操作レスポンスを犠牲にしない。

---

## 将来拡張の余地

- **Online**: `BattlePlayer` を `Local Human` / `CPU` / `Remote Human` の共通インターフェースとして設計する。MVP に Network Layer は導入しない
- **高速化**: GDScript のみで実装し、Profiler でボトルネックが確認された場合のみ GDExtension（C++ / Rust）を検討する。
  対象候補は CPU 探索、Board Evaluation、大量盤面 Simulation、Search Tree、Replay 高速処理。**過剰最適化を先に行わない**
