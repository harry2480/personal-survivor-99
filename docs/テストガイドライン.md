# Project 99 テストガイドライン

Godot 4 プロジェクトにおけるテストの種類・対象・書き方・運用をまとめたガイドライン。
品質ゲートの全体像は [品質チェック・テスト規約.md](品質チェック・テスト規約.md) を参照。

---

## テストの種類と構成

| 種類 | 配置場所 | 実行 | 用途 |
|------|----------|------|------|
| Core Unit Test | `tests/core/` | Headless | Board / Piece / Rotation / Line Clear / Attack 計算などの純粋ロジック |
| Battle Test | `tests/battle/` | Headless | Target / Garbage Routing / KO / Ranking / Multiplier |
| CPU Test | `tests/cpu/` | Headless | Strength パラメータの反映、CPU 同士の対戦完走 |
| Integration Test | `tests/integration/` | Headless | 2〜99 人 Battle の完走、Pause / Restart / 連戦 |
| Controller Test | 手動 | 実機 | Pro Controller の接続・操作・再接続 |
| UI 視認性チェック | 手動 | 実機 | Main Board / Opponent Grid / HUD の見やすさ |
| Performance Test | 手動 + 計測 | 実機 | 99 人戦の FPS、入力遅延、メモリリーク |

### Test Framework

**GUT 9.7.1** を採用する（Phase 0 / #18 で確定）。

- `addons/gut/` にバージョン固定で同梱している。更新手順は [addons/README.md](../addons/README.md)
- 対応 Godot は 4.7.x で、`.godot-version`（4.7.2-stable）と一致する
- テストは `extends GutTest` で書き、ファイル名を `test_*.gd`、テスト関数名を `test_*` にする
- 実行対象ディレクトリ・ログレベルなどの既定値は `.gutconfig.json` に定義する
- Headless で実行できないテストは自動テストに含めない（手動検証として扱う）

```sh
scripts/run-tests.sh                        # tests/ 配下をすべて実行
scripts/run-tests.sh -gdir=res://tests/core # ディレクトリを絞る
scripts/run-tests.sh -gunit_test_name=test_seeded_rng_is_reproducible
```

テストが 1 件でも失敗すると非 0 の終了コードで終わるため、CI ゲートとして使える。
Godot はスクリプトエラーが出ても終了コード 0 を返すが、GUT は `push_error` と
エンジンエラーも失敗として扱う（`.gutconfig.json` の `failure_error_types` 既定値）。

## Core Unit Test

### 対象

```text
7-Bag
Collision
Rotation
Wall Kick
Hold
Ghost
Hard Drop
Lock
Line Clear
Combo
B2B
T-Spin
Perfect Clear
Garbage
Cancellation
Attack Calculation
KO
Ranking
Target Selection
```

### 設計方針

- **Game Core は UI / Audio / Scene / File System に依存しないため、Scene Tree なしで直接テストする**
- 盤面は文字列や配列リテラルで組み立て、期待結果と比較できる形にする
- 時間依存の処理（Gravity, Lock Delay, DAS/ARR）は実時間を待たず、**delta / tick を明示的に与えて進める**
- 乱数は Seed を固定して注入する。グローバル乱数に依存したテストを書かない
- バランス値はテスト用の Rule / Balance データを注入する。本番設定値の変更でテストが壊れないようにする

```gdscript
func test_7bag_contains_each_piece_once() -> void:
    var rng := RandomNumberGenerator.new()
    rng.seed = 12345
    var bag := PieceRandomizer.new(rng)

    var drawn: Array[int] = []
    for i in range(7):
        drawn.append(bag.next_piece())

    drawn.sort()
    assert_eq(drawn, [0, 1, 2, 3, 4, 5, 6])
```

### 必ずテストを追加するケース

- Attack 計算、Garbage 相殺、T-Spin / B2B / Perfect Clear の判定ロジックの変更
- Rotation / Wall Kick テーブルの変更
- Target 選択ロジックの変更
- バグ修正（再発防止テストとして必須）

## Battle Test

### 対象と最低限の検証

- Target 安全性
  - 自分を狙わない
  - Dead Player を狙わない
  - Target 消失時に Crash しない
  - 残り 1 人になったら Target 処理を停止する
  - Invalid ID を安全に処理する
- Garbage Routing: Delay 経過後に適用される / 処理順序が保証される
- KO: 脱落後に Simulation・Attack が停止し、Target 対象から除外される
- Ranking: 脱落時の生存人数から順位が確定する（残り 10 人で脱落 → Rank 10、最後の 1 人 → Rank 1）
- Multiplier: 閾値到達で Stage が上がる

## CPU Test

最低限、以下を検証する。

- Strength を変更すると挙動が変化する
- Reaction Time が反映される
- PPS が反映される
- Misdrop Rate が反映される
- Search Depth が反映される
- Misdrop 0% 設定で正しく動作する
- **Extreme CPU が通常 CPU より高い Performance を示す**
- Machine CPU が設定上限で安定動作する
- CPU 同士の Battle が完走する

### 設計方針

- 強さの比較は 1 試合で判定せず、Seed を変えた複数試行の統計（勝率 / 平均 Rank / 平均 Attack）で判定する
- 「強さ」を検証するテストはフレーキーになりやすいため、閾値に十分なマージンを取る
- CPU 同士の対戦を Benchmark として再利用できるようにする（Seed 固定で再現可能にする）

要件定義 §91 の「情報密度のために Main Board の視認性を犠牲にしない」は
自動テストで測れないため、実際に動かして確認する（#48〜#50 の完了条件）。

### Main Player Board（#48）

- [ ] Fixed Blocks / Active Piece / Ghost が一目で区別できる
- [ ] Ghost が Active Piece と紛らわしくない

### Opponent Grid（#49）

## Performance Test（手動・計測）

Apple Silicon Mac で通常 99 人戦を実行し、以下を確認する。

- 平均 60 FPS 以上
- 継続的な重大 Frame Drop がない
- 操作不能 Stall がない
- Human Input に顕著な遅延がない
- 連続試合で Memory Leak がない
- 99 Player Battle が完走可能

Extreme / Machine CPU では、必要に応じて Search Depth や Detailed CPU 数を調整して性能を維持する。
計測値は Debug Overlay（FPS / Frame Time / Detailed CPU Count / Memory 等）で確認する。

## テスト作成時の注意事項

- **Scene Tree に依存しない**: Core / Battle のテストで Scene をロードしない。ロジックを直接呼ぶ
- **実時間を待たない**: `await get_tree().create_timer(...)` でテストを遅延させない。tick を進める
- **Seed を固定する**: 再現しないテストを残さない。失敗時は Seed をログへ出す
- **describe 相当のグループ化**: 関連ケースはファイル・クラス単位でまとめ、テスト名で意図を説明する
- **後片付け**: ファイルを書くテストはテスト専用パスを使い、実行後に削除する
