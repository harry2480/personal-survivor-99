# Project 99 品質チェック規約

Godot 4 + Typed GDScript プロジェクトにおける品質ゲートの規約。
テストの書き方と対象は [テストガイドライン.md](テストガイドライン.md)、CI の構成は [インフラストラクチャ規約.md](インフラストラクチャ規約.md) を参照。

---

## Quality Check 一覧

| チェック | 対象 | コマンド | 実行 |
|---|---|---|---|
| Static Check（Lint / フォーマット / 命名規約 / 依存方向） | 全ソース | `scripts/static-check.sh` | CI 必須 |
| Import / 起動検証 | プロジェクト全体 | `scripts/verify-godot.sh` | CI 必須 |
| Core / Battle / CPU Unit Test | `tests/core/` `tests/battle/` `tests/cpu/` | `scripts/run-tests.sh` | CI 必須（Headless） |
| Integration Test | `tests/integration/` | `scripts/run-tests.sh` | CI 必須（Headless） |
| Build Validation（macOS Export） | プロジェクト全体 | `scripts/export-macos.sh` | CI 必須（macOS runner） |
| Controller Test | Pro Controller 実機 | 手動 | 手動（Release 前） |
| Performance Test | 99 人戦 | 手動 | 手動（Release 前） |

いずれも CI とローカルで同じスクリプトを実行する。実機が必要な Controller Test と
Performance Test は自動化できないため、集約 check には含めない。

### Static Check の内訳

`scripts/static-check.sh` が実行する内容。

| # | 検査 | ツール |
|---|---|---|
| 1 | GDScript の構文・未使用・命名規約 | `gdlint`（gdtoolkit、`ci/requirements-static-check.txt` でバージョン固定） |
| 2 | フォーマット崩れ | `gdformat --check`（書き換えはしない） |
| 3 | ファイル・ディレクトリの snake_case | 自前の検査（要件定義 §119） |
| 4 | レイヤー依存方向 | 自前の検査（`res://` 参照の走査） |
| 5 | シェルスクリプト | `shellcheck`（未導入なら省略） |
| 6 | GitHub Actions ワークフロー | `actionlint`（未導入なら省略） |

4 は GDScript に依存方向を機械検証する標準ツールがないため、`core/` が
`ui` `scenes` `audio` `input` `battle` `cpu` を、`battle/` `cpu/` が `ui` `scenes` `audio` を
`res://` 参照していないかを走査している。`preload` を使わない動的な参照までは追えないため、
レビューでの確認（後述）と併用する。

## 実行フロー

```text
PR 作成 / 更新 / push
  └── CI（.github/workflows/ci.yml）
      ├── Static Check ........... ubuntu
      ├── Import / 起動検証 ...... ubuntu
      ├── Headless テスト ........ ubuntu
      ├── macOS Export Validation  macOS
      └── CI ステータス確認 ...... 上記すべての成否を集約
```

`main` の branch protection では `CI ステータス確認`（job ID `ci-status`）だけを
required check に指定する（[loop-engineering.md](loop-engineering.md)）。

全ステップがパスするとマージ可能になる。コード変更後は必ずローカルでも自動テストを実行し、
全パスすることを確認してから PR を作成する。

## 型の扱い

- **Typed GDScript を必須とする。** 変数・引数・戻り値に型注釈を付ける
- 戻り値のない関数も `-> void` を明示する
- `Variant` は外部入力（JSON パース結果など）の受け口に限定し、**直後に型付きモデルへ変換する**
- `Dictionary` を状態の器として持ち回らない。専用 Class / Resource を定義する
- 型が緩い箇所を残す場合は、理由をコメントで明記する

## レイヤー依存のチェック

[アーキテクチャ.md](アーキテクチャ.md) の依存方向 `Presentation → Battle → Game Core` を守る。
GDScript には依存方向を機械的に検証する標準ツールがないため、以下で担保する。

- **レビュー時に import / preload / class_name 参照の向きを確認する**
- `core/` 配下のスクリプトが `ui/` `scenes/` `audio/` `battle/` `cpu/` を参照していないこと
- `battle/` `cpu/` が `ui/` `scenes/` を参照していないこと
- 上記を検出する簡易スクリプト（`core/` 配下の参照先を grep で検査する等）を CI に追加してもよい

### レビューで必ず見る観点

- Game Core が UI / Audio / Controller / Scene / Animation / File System / Opponent Grid を知らないか
- UI が Game Core / Battle の内部状態を直接書き換えていないか
- Magic Number が書かれていないか。バランス値が `config/` に外部化されているか
- 物理ボタン番号がゲームロジックに漏れていないか
- Autoload（Singleton）を不要に増やしていないか

---

## 決定論の担保

- 乱数は Seed 付き `RandomNumberGenerator` を注入する。グローバル乱数を直接使わない
- シミュレーションは Render FPS に依存しない（時間ベース・tick ベース）
- 同一 Seed・同一入力列で結果が再現することを、テストで確認できる範囲は必ず確認する
- 再現しない不具合を見つけたら、まず Seed とログを残せる状態にしてから修正に入る

## パフォーマンス基準

Apple Silicon Mac / 99 人戦で以下を満たすこと。

- 平均 60 FPS 以上
- 継続的な重大 Frame Drop がない
- 操作不能 Stall がない
- Human Input に顕著な遅延がない
- 連続試合で Memory Usage が増え続けない

**最適化は計測後に行う。** Profiler でボトルネックを特定せずに GDExtension 化や
アルゴリズム変更を行わない。負荷削減の優先順位は以下に従う。

```text
Human Input > Game Core > Battle State > Rendering > CPU Search Depth > Visual Effects
```

## マージ条件

- CI の必須チェックがすべて成功していること
- 自動テストの追加・更新が必要な変更（[テストガイドライン.md](テストガイドライン.md) の「必ずテストを追加するケース」）で、テストが追加されていること
- 依存方向・Coding Rules の違反がないこと
- 未解決のレビュー指摘がないこと

Loop 運用時の追加ゲートは [loop-engineering.md](loop-engineering.md) に従う。
